# Paso 9 — feed incremental v1

Candidata SQL para staging: contador transaccional por rancho, epoch y feed append-only de cambios en las tablas actuales. Backfill bajo bloqueo; triggers capturan altas, cambios, tombstones y borrados físicos de animales, jornadas y configuración. No usar timestamp ni secuencia PostgreSQL como cursor. El bloqueo del contador se mantiene hasta commit, evitando huecos por transacciones que terminan en orden distinto. Rollback revierte contador y feed. Transacciones que mezclan varios animales/ranchos pueden sufrir deadlock; PostgreSQL aborta una y el cliente debe reintentar. No usar TRUNCATE en tablas fuente; no cubierto por triggers. RPC autenticada sync_pull_changes(p_owner,p_after,p_epoch,p_limit) verifica membresía, máximo 100 filas. epoch distinto o cursor futuro obliga reconstrucción de la base remota, nunca borrar outbox. Retención indefinida provisional; feed contiene snapshots completos por ficha, no deltas por campo; coste de almacenamiento y ancho de banda a medir. No implementar pruning sin protocolo de resnapshot. La respuesta incluye head, nextCursor, hasMore. El consumidor valida secuencia contigua y aplica página a copia confirmada; persistir copia+cursor en UNA transacción, no tocar cola local ni datos editados. El módulo puro web y equivalente móvil son preparación: todavía no están conectados al ciclo existente ni persisten cursor. No habilitar producción hasta staging, pruebas de dos conexiones concurrentes, revocación, rollback, tombstone, paginación y restauración. El feed no sustituye auditoría y no está diseñado para restaurar backups.
